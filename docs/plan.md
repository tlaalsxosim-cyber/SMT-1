# AI 기반 일일 배송 최적화 시스템 기획서

작성일: 2026-09-15 · 버전 2.1 (무저장 구조 확정 — DB 미사용 · 매회 파일 업로드 · 결과 엑셀 다운로드)

---

## 1. 개요

### 1.1 목적
출고등록현황(일일 변동)과 차량톤수 마스터(고정)를 입력받아, 기사 9명·총 12회전에 대한 배차 코스를 자동 편성하는 웹 앱을 구축한다. 톤수별 적재·회전·업체수 제약과 납품시간을 지키고, 마지막 하차지가 기사 거주지(도착지) 인근이 되도록 하여 공차 귀가에 따른 유류비를 최소화한다. 소화하지 못한 물량은 버리지 않고 권역별 "기타"로 묶어 용차 판단 자료로 제공한다.

### 1.2 확정 전제 조건
| 항목 | 확정 내용 |
|---|---|
| 출발지 | 평택센터 단일 출발 |
| 지도·도로 기능 | TMAP API로 통일 (App Key 발급 완료, Free 상품 사용 신청 완료 전제) |
| 적재 기준 | 차량톤수 파일의 최소·최대 박스 수량 그대로 적용 |
| 조기 납품 제한 | 납품시간 9시 이전 업체는 기사당 1곳까지만 배차 |
| 데이터 보관 | **데이터베이스 미사용 (무저장 구조).** 출고등록현황.xlsx와 차량_톤수.xlsx를 매회 함께 업로드하고, 결과는 엑셀 파일로 다운로드. 서버·브라우저에 데이터를 남기지 않음 |

### 1.3 무저장(Stateless) 구조 원칙
매 배차는 독립적인 1회 실행이다. 입력은 업로드한 파일 2개가 전부이고, 출력은 다운로드한 엑셀 1개가 전부다.

1. **입력**: 출고등록현황.xlsx (일일 변동) + 차량_톤수.xlsx (기사·톤수·적재범위·회전수·도착지 — 수정이 생기면 파일을 고쳐서 다시 업로드)
2. **처리**: 업로드된 데이터는 브라우저/서버 메모리에서만 사용하고 세션 종료 시 소멸. DB·영구 저장소 없음
3. **출력**: 배차 결과 엑셀 다운로드. 화면은 확인·검토용이며, 보관·공유·수정의 기준 문서는 다운로드한 엑셀
4. **효과**: TMAP 약관(경로 데이터 24시간 이상 저장 금지)과 자연스럽게 부합하고, 서버 구축·운영 부담과 개인정보·키 관리 리스크가 최소화됨. 대신 좌표 캐시가 없으므로 지오코딩은 매회 호출한다 (2.3절 — 무료 한도 대비 충분)

### 1.4 설계의 뼈대 — 3계층 역할 분담
**"어느 차량이 어디를 갈지(차량 간 배분)"는 자체 로직, "차량 안에서의 방문순서와 도로"는 TMAP, "비정형 텍스트의 해석·분류"는 생성형 AI**가 맡는다. 이 분리가 전체 설계의 기준이다.

| 계층 | 담당 | 담당 업무 |
|---|---|---|
| ① 생성형 AI (LLM) | 데이터 해석·분류 | 납품처 문자열 파싱, 납품시간·배송조건 구조화, 주소 정제 제안, 배차 결과 요약 |
| ② 자체 배차 로직 (규칙 기반) | 차량 간 배분 | 톤수별 적재 조합, 회전 배정, 권역 묶음, 9시 전 제한, 기타 분류 |
| ③ TMAP API | 좌표·순서·경로·지도 | 지오코딩, 차량 1대의 방문순서 최적화, 실도로 거리·시간·경로선, 지도 표시 |

## 2. TMAP API 활용 설계 (③ 계층)

### 2.1 사용 API 5종
| API | 엔드포인트 | 시스템 내 역할 | 무료 한도(일) |
|---|---|---|---|
| 지오코딩 | GET /tmap/geo/fullAddrGeo | 납품처주소·기사 도착지 → 위경도 변환 | 20,000건 |
| 지도 (Map JS) | /tmap/jsv2 | 대시보드 지도, 마커, 경로선 표시 | 100,000건 |
| 자동차 경로안내 | POST /tmap/routes | 두 지점 간 실도로 거리·시간 (배차 로직의 거리 근거) | 1,000건 |
| 다중 경유지 | POST /tmap/routes/routeSequential30 | 확정된 순서의 도로 경로선 + 구간별 도착예정시각 | (경로안내 한도 공유) |
| 경유지 최적화 | POST /routes/routeOptimization10 | 차량 1대(회전 1개)의 방문순서 자동 최적화 | 50건 |

### 2.2 API별 상세 설계

**① 지오코딩 (fullAddrGeo)**
- 파라미터: `version=1, format=json, coordType=WGS84GEO, fullAddr={주소}` / 헤더 `appKey`
- 좌표 추출 규칙: 도로명 매칭 시 `newLat/newLon`, 지번 매칭 시 `lat/lon` — 두 필드 모두 확인하는 분기 필수. 배송 실무에는 건물 입구 좌표 `newLatEntr/newLonEntr` 우선 사용
- 성공 판정: `totalCount` 기준. `"0"` = 변환 실패 → 지도에 올리지 않고 **"주소 확인 필요" 목록으로 분리** (기타 패널에 표시)
- 검증: `newRoadName + 건물번호`를 입력 주소와 교차 확인해 오배차 방지. `remainder` 필드에 값이 있는 행 = 주소 정제 대상 자동 탐지 (→ 생성형 AI 정제 제안과 연결, 4.2절)
- **무저장 구조이므로 좌표 캐시 없이 매회 전체 주소를 변환한다** (일 65건 내외 — 무료 20,000건 대비 충분). 지오코딩 호출을 더 줄이고 싶다면, 결과 엑셀의 "좌표" 시트를 다음 날 출고등록현황과 함께 참고 자료로 재업로드하는 선택 기능을 둘 수 있다 (약관상 저장 허용 범위는 운영 전 재확인)

**② 지도 표시 (Map JS jsv2)**
- 평택센터는 구분 마커, 납품처는 기사별 색상 마커, 클릭 시 납품처명·박스·납품시간 팝업
- 모든 마커가 한 화면에 들어오도록 자동 범위 조절, 좌표 없는 배송지는 지도에서 제외
- 회전별 경로선은 routeSequential30 응답의 LineString 좌표로 그린다. **좌표 순서 주의**: 응답은 [경도, 위도], Tmapv2.LatLng은 (위도, 경도) — 반전 필수

**③ 자동차 경로안내 (/tmap/routes)**
- Body: `startX/startY, endX/endY, reqCoordType/resCoordType=WGS84GEO, searchOption=0` (X=경도, Y=위도 순서 주의)
- 응답: `features[0].properties.totalDistance`(m) · `totalTime`(초) → 화면에는 항상 km·분으로 변환 표시
- 용도: 자체 배차 로직이 쓰는 센터~납품처, 납품처~기사 도착지 간 **실도로 거리 행렬**의 근거. 호출량 관리를 위해 1차 후보 선정은 직선거리 근사, 최종 검증·표시에만 실도로 값 사용 (2.3절)

**④ 다중 경유지 (routeSequential30)**
- 방문 순서가 **이미 정해져 있을 때** 사용 — 최적화 API가 정한 순서를 넣어 실도로 경로선을 그리는 마무리 담당
- Body: `startName/startX/startY, startTime(yyyyMMddHHmm 12자리), endName/endX/endY, viaPoints[]`
- **endX/endY에 기사 도착지(거주지) 좌표를 지정**하여 귀가 구간까지 포함한 경로·시간을 계산 → 유류비 동선이 API 수준에서 반영됨
- 응답의 구간별 거리·시간으로 각 납품처 도착예정시각을 산출, 배차표에 기재

**⑤ 경유지 최적화 (routeOptimization10)**
- **회전(차량 1대의 1회 운행) 단위로만 호출** — 하루 50건 무료로 가장 귀한 자원. 배차 확정 시 회전당 1회, 일일 최대 12건 사용
- Body: 출발지=평택센터+`startTime`, **도착지=기사 도착지(거주지)**, viaPoints=해당 회전의 납품처들(최대 10개, 우리 회전은 최대 5업체라 여유)
- 응답: `pointType "B1"` Feature의 등장 순서 = 최적 방문순서, 납품처별 `arriveTime` 자동 계산
- **arriveTime을 납품시간창과 대조**하여 시간 위반 여부를 검증 — 위반 시 자체 로직이 조합을 재구성 후 재호출(재시도 1회 한도)

### 2.3 일일 API 호출량 설계 (무료 한도 내 운영)
| API | 일일 예상 호출 | 한도 대비 |
|---|---|---|
| 지오코딩 | 매회 전체 변환: 납품처 55 + 기사 도착지 9 = 65건 내외 | 20,000건 — 여유 |
| 경로안내 | 최종 검증·표시용 20~50건 (1차 후보 선정은 직선 근사로 대체) | 1,000건 — 여유 |
| 다중 경유지 | 회전당 1건 = 최대 12건 | 경로안내 한도 공유 — 여유 |
| 경유지 최적화 | 회전당 1건 + 재시도 = 최대 24건 | **50건 — 버튼 연타 방지 필수** |
| 지도 | 화면 조회 시 | 100,000건 — 여유 |

최적화 API 보호 장치: 배차 실행 버튼에 실행 중 잠금, 개발·시연 시에는 저장된 응답을 재생하는 **Demo Mode** 제공, 일일 호출 카운터 표시.

### 2.4 약관·보안 준수 사항
- 경로 응답의 좌표 데이터는 **약관상 24시간 이상 저장·재사용 금지** — 무저장 구조라 원천적으로 준수됨 (DB 없음, 매회 호출)
- App Key는 코드에 하드코딩하지 않고 **환경변수(TMAP_APP_KEY)** 로 관리, 키 미설정 시 안내 배너 표시. 메신저·공개 저장소 공유 금지, 노출 시 즉시 재발급, 교육용·운영용 키 분리
- 브라우저 직접 호출 시 CORS 차단 가능 → **서버(프록시) 경유 호출** 구조로 설계. 401은 키 누락·미승인 상품, 400은 Body 형식 오류(주석·축약 금지, startTime 12자리)로 구분 대응
- 무료 제공량·상품 구성은 변경될 수 있으므로 운영 전 SK open API 요금 페이지 기준 재확인

## 3. 생성형 AI 활용 설계 (① 계층)

TMAP이 처리할 수 없는 **비정형 텍스트의 해석·분류**를 생성형 AI가 담당한다. 원칙: AI 출력은 항상 구조화된 JSON으로 받고, 규칙으로 검증 가능한 항목은 규칙 검증을 통과해야만 배차에 반영한다.

### 3.1 분류·구조화 대상
| 작업 | 입력 (비정형) | AI 출력 (구조화) |
|---|---|---|
| 납품처 문자열 파싱 | `5/굿엉클스/하남/창고안적재(비대면)` | 업체명, 권역, 특이사항 태그. 슬래시 규칙을 벗어난 변형 표기도 해석 |
| 납품시간 구조화 | `~13:00`, `8~11또는13~14:30(점심11:30~13)`, `오전 하차 권장`, `13시30분전` | 시간창 배열 [{시작, 종료}], 점심 제외 구간, 권장/필수 구분 |
| 배송조건 분류 | 특이사항 텍스트 | 조기납품(9시 전) 플래그, 비대면·안전화 착용·도크 지정 등 하차 조건 태그, 배차 제약 여부 판단 |
| 주소 정제 제안 | 지오코딩 실패 주소, `remainder` 값이 있는 주소 | 표준 주소 후보 제안 → 담당자 확인 후 재변환 (자동 확정 금지) |
| 배차 결과 요약 | 배차 결과 데이터 | 기사별 브리핑 문장, 기타 물량에 대한 용차 판단 참고 요약 |

### 3.2 검증 규칙
- 시간창 구조화 결과는 파서로 형식 검증(시작<종료, 00:00~24:00 범위), 원문과 나란히 화면에 표시해 담당자가 확인
- "조기납품" 등 배차 제약에 직접 쓰이는 플래그는 AI 판단 + 규칙 판단(마감 ≤ 09:00)을 모두 통과한 경우만 강제 적용, 불일치 시 담당자 확인 목록으로 분리
- 주소 정제는 제안까지만 — 좌표 확정은 지오코딩 재호출 성공(totalCount ≥ 1, newRoadName 교차 확인)으로만 이루어진다

## 4. 자체 배차 로직 (② 계층) — 차량 간 배분 규칙

TMAP은 "차량 한 대 안의 순서"만 정한다. **어느 차량이 어디를 가는가**는 아래 자체 규칙으로 결정한다.

1. **배차 대상 필터**: 배송방법 빈값 행만 대상 (픽업·이체·취소 자동 제외). 납품처+주소 단위로 재고단위수량 합산 = 박스 수량
2. **적재 범위 강제**: 회전 박스 합계는 차량 마스터의 최소~최대수량 내. 최소 미달 차량은 출고하지 않음
3. **업체 수 범위**: 1~4톤 1회전 3~5업체 / 5·10톤 2회전 회전당 1~2업체 (마스터 값 기준)
4. **권역 묶음**: 지오코딩 좌표 기준 인접 업체 취합. 기사 도착지(거주지) 인근 권역을 해당 기사에게 우선 배정
5. **9시 전 납품 제한**: 기사당 1곳까지만, 2회전 배정 불가
6. **2회전 시간 실현성**: 1회전 종료(납품 대기 포함) + 센터 복귀 + 재상차 30분을 추정해 시간 내 도달 가능한 업체만 배정. 최종 검증은 TMAP arriveTime으로 수행
7. **초과 물량 자동 분할**: 단일 납품처가 최대 적재(1,200박스) 초과 시 분할 (예: 미담 1,373 → 1,200 + 173)
8. **전량 소진 원칙**: 12회전 초과 물량은 권역별 "기타"로 묶어 제시 — 용차 투입은 담당자 판단

## 5. 처리 파이프라인 (E2E)

1. **Excel 업로드 (2개 파일)** — 출고등록현황.xlsx 파싱·제외 건 집계 + 차량_톤수.xlsx 파싱(기사·적재범위·회전수·도착지 검증: 필수 컬럼·수치 범위 확인) [자체]
2. **조건 구조화** — 납품처·납품시간·특이사항 해석 [생성형 AI] → 규칙 검증 [자체]
3. **좌표 변환** — 신규·변경 주소 지오코딩, 실패분 "주소 확인 필요" 분리 [TMAP ①]
4. **차량 간 배분** — 적재·회전·업체수·조기납품 제약 하에 회전별 납품처 조합 결정 [자체]
5. **방문순서 최적화** — 회전당 1회, 출발=센터·도착=기사 거주지로 최적 순서 산출 [TMAP ⑤]
6. **시간 검증** — arriveTime vs 시간창 대조, 위반 시 4단계로 되돌아가 조합 재구성 [자체 + TMAP]
7. **경로 확정** — 확정 순서로 실도로 경로선·구간 시간 산출 [TMAP ④]
8. **결과 출력** — TMAP 지도 표시 [TMAP ②], 화면 검토 후 **결과 엑셀 다운로드** (5.1절), AI 요약 브리핑 [자체 + 생성형 AI]. 다운로드와 함께 세션 데이터 소멸

## 6. 화면 설계 (4개 탭)

**① 배차 보드**: TMAP 지도(jsv2 — 센터·기사별 색상 마커·실도로 경로선, 마커 클릭 팝업), 기사별 배차 티켓(회전별 순서·박스·TMAP 도착예정시각·적재율·특이사항 태그·귀가 거리), 기타(미배차) 권역별 패널 + 주소 확인 필요 목록, **결과 엑셀 다운로드**, AI 요약 브리핑
**② 데이터 업로드**: 출고등록현황.xlsx + 차량_톤수.xlsx 두 파일 드래그 업로드 → 파싱·AI 구조화 결과 미리보기(원문과 해석 나란히, 조기납품 표시, 담당자 확인 목록). 차량 마스터도 화면 편집이 아닌 **파일 수정 후 재업로드**가 기준 — 화면에서는 확인만
**③ 결과 다운로드**: 배차 확정 후 결과 엑셀(5개 시트) 다운로드 버튼. 다운로드 전 이탈 시 결과가 사라짐을 안내
**④ 설정**: 센터 좌표·출발시각(기본값 내장, 세션 한정 변경), TMAP 키 상태(환경변수), API 일일 호출 카운터, Demo Mode 전환 — 설정도 저장하지 않으며 매 실행 기본값에서 시작

## 7. 검증 현황과 단계별 로드맵

| 단계 | 내용 | 상태 |
|---|---|---|
| 1단계 | 근사 좌표 + 직선거리 프로토타입으로 배차 규칙 검증 | **완료** — 실데이터 55개 납품처·8,043박스 기준 11/12회전, 5,859박스 배차, 제약 위반 0건, 시간 경고 0건, 기타 2,184박스 권역별 묶음 |
| 2단계 | TMAP 5종 API 연동 (프록시 서버 + 환경변수 키 관리 + Demo Mode) | 착수 — App Key 발급 완료 |
| 3단계 | 생성형 AI 조건 구조화 모듈 탑재, 검증 UI | 2단계와 병행 |
| 4단계 | 실운행 대조 — TMAP arriveTime vs 실제 도착 실적 비교, 파라미터(하차 시간·2회전 기준) 보정 | 운영 후 |

1단계 프로토타입에서 거리 계산은 `distKm` 단일 함수로 분리되어 있어, 2단계에서 TMAP 경로안내·최적화 API로 교체하는 지점이 명확하다.

## 8. 향후 과제

1. 기사 도착지 정식 주소 확보 및 지오코딩 갱신 (귀가 동선 정밀도)
2. 배차 결과 수동 조정 UI (드래그 이동 후 재계산 — 최적화 API 재호출은 조정된 회전만, 조정 결과도 엑셀로만 보관)
3. 최적화 호출량 증가 대비 유료 플랜 검토 기준 수립 (일 50건 초과 시)
4. 실적 비교는 다운로드한 배차표 엑셀과 실제 운행 기록을 대조하는 방식으로 수행 (무저장 원칙 유지) — 업체별 하차 시간·시간대별 속도 보정 근거로 활용
5. 무저장 구조의 한계 모니터링: 매회 업로드 부담·좌표 재변환이 실제 운영에서 병목이 되면, 그 시점에 최소 범위(좌표 캐시 등)의 저장 도입을 재검토
