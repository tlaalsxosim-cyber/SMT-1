## 1. 배경과 문제 정의

평택센터는 매일 아침 출고등록현황을 받아 기사 9명에게 배송 코스를 **수작업으로** 편성한다. 현재 편성 과정에는 네 가지 구조적 문제가 있다.

1. **제약 조건이 사람 머릿속에만 있다.** 톤수별 최소·최대 적재량, 회전당 업체 수, 납품 시간창, 조기납품 제한을 동시에 만족시키는 조합을 매일 손으로 찾는다.
2. **납품 조건이 비정형 텍스트로 흩어져 있다.** 납품처명 문자열(`5/굿엉클스/하남/창고안적재(비대면)`), 납품시간 컬럼, 비고 필드에 조건이 분산되어 있고 서로 어긋나는 경우가 실재한다(§5.3).
3. **귀가 동선이 고려되지 않는다.** 마지막 하차지가 기사 거주지에서 멀면 공차 귀가 거리가 그대로 유류비가 된다.
4. **소화 못 한 물량의 판단 근거가 없다.** 용차 투입 여부를 감으로 결정한다.

2026-09-15 실데이터 기준으로 이 문제의 규모는 다음과 같다.

| 지표 | 실측값 |
|---|---|
| 출고 오더 행 | 304행 (배차 대상 287행 / 제외 17행) |
| 배차 대상 납품처 | 55곳 (납품처명 + 주소 기준) |
| 총 물량 | 8,043 박스 |
| 가용 차량 | 기사 9명 · 총 12회전 |
| 이론 최대 적재량 | 8,225 박스 (물량 대비 여유율 2.3%) |
| 회전당 업체 수 상한 합계 | 42곳 (< 납품처 55곳) |

**즉, 적재량으로는 아슬아슬하게 맞지만 "업체 수" 제약 때문에 최소 13곳은 구조적으로 당일 배차가 불가능하다.** 1단계 프로토타입이 11/12회전·5,859박스 배차, 기타 2,184박스로 수렴한 것은 이 구조적 한계의 반영이며, 시스템의 역할은 "전부 싣는 것"이 아니라 **제약을 지킨 최적 조합을 만들고, 남는 물량을 근거와 함께 드러내는 것**이다.

## 3. 사용자와 사용 시나리오

| 사용자 | 설명 | 핵심 니즈 |
|---|---|---|
| 배차 담당자 (주 사용자, 1~2명) | 매일 아침 배차 편성 | 빠른 편성, 조건 위반 사전 경고, 수정 가능한 엑셀 |
| 물류 관리자 | 용차 투입·비용 의사결정 | 미배차 물량의 권역·사유·박스 수 |
| 기사 (간접) | 배차표 수령자 | 방문 순서, 도착예정시각, 하차 조건, 귀가 동선 |

**주 시나리오 (Happy Path)**
1. 담당자가 아침에 ERP에서 `출고등록현황.xlsx`를 내려받는다.
2. 웹앱 "데이터 업로드" 탭에 출고등록현황과 차량_톤수 두 파일을 드래그한다.
3. 파싱·AI 구조화 결과 미리보기에서 원문과 해석을 나란히 확인하고, 담당자 확인 목록(시간창 불일치·조기납품 후보·주소 이상)을 승인한다.
4. "배차 실행"을 누른다. 좌표 변환 → 차량 간 배분 → 순서 최적화 → 시간 검증 → 경로 확정이 순차 진행된다.
5. "배차 보드" 탭에서 지도와 기사별 티켓, 기타(미배차) 패널을 검토한다.
6. "결과 다운로드"에서 엑셀을 받는다. 이후 보관·공유·수정은 이 엑셀이 기준이다.

#### 5.1.1 납품처 문자열 구조

관측된 패턴: `{코스코드}/{업체명}/{권역}/{조건}` — 55건 중 49건이 4토큰, 3건이 5토큰, 3건이 3토큰.

```
5 / 굿엉클스        / 하남              / 창고안적재(비대면)
3 / 스마트푸드      / 오산              / 9시~14시 / 안전화필히착용     ← 5토큰
5 / 신선한식탁      / 인천                                              ← 3토큰
4 / 자연이랑        / 이천(양녕로)      / 9:30~15시(12~13시점심)
```

**선두 코스코드의 분포** — 원거리일수록 값이 커지는 경향이 뚜렷하다.

| 코스코드 | 업체 수 | 권역 |
|---|---|---|
| 3 | 12 | 평택·오산·안성·용인·천안 (센터 인접 남부) |
| 4 | 12 | 이천·화성·안산·의왕·성남·서울 (중부) |
| 5 | 29 | 인천·시흥·김포·고양·하남·광주·남양주·구리·아산 (수도권 북서) |
| 10 | 1 | 청주 |
| 20 | 1 | 익산 |

→ 권역 묶음의 **1차 힌트로 활용**하되, 정확한 정의는 현업 확인 필요 (§14 OI-1).

#### 5.2.1 도착지 데이터 품질 (실측 이슈)

9건 중 7건이 **시·군청 대표 주소** 형태다 (하남시청·시흥시청·이천시청·수원시청·평택시청·화성시청·남동구청). 실제 거주지가 아닌 권역 대표점으로 기재된 것으로 보인다.

- 유종수(1.5톤)·곽창훈(10톤) 두 기사의 도착지가 **동일 주소**(용인시 처인구 중부대로 1199)
- 김남성 도착지 `경기도 화성시 만세구 남양읍 시청로 159` — **"만세구"는 존재하지 않는 행정구역** (지오코딩 실패 예상)

→ 시스템은 이를 그대로 수용하되, 업로드 검증에서 **지오코딩 실패 도착지를 경고**하고, 귀가 거리 수치가 "권역 대표점 기준 근사"임을 결과 엑셀에 명시한다. 정식 주소 확보는 별도 과제 (§14 OI-4).

### 5.3 데이터 품질 실측 결과 — AI 계층이 필요한 이유

2026-09-15 실데이터를 전수 검사한 결과다. **이 항목들이 생성형 AI 계층의 구체적 요구사항을 정의한다.**

#### (1) 납품시간 컬럼과 납품처명 문자열의 불일치 — 6건

납품시간 컬럼만 신뢰하면 배차가 틀어진다. 두 소스를 **대조·병합**해야 한다.
불일치는 심각도가 다른 두 종류로 나뉜다.

**경계 불일치 (2건)** — 컬럼이 실제보다 늦은 마감을 담고 있다. 시간 위반 배송에 직결된다.

| 업체 | 납품처명 원문 | 납품시간 컬럼 | 문제 |
|---|---|---|---|
| 지케이(광주새말길) | `8~15시(12시30분~13시30분제외)` | `8:00~17:00` | **마감 2시간 과대** |

**컬럼 결손 (4건)** — 컬럼이 비어 있고 조건이 납품처명에만 있다. 파싱으로 전량 회수 가능하다.

| 업체 | 납품처명 원문 | 회수되는 시간창 |
|---|---|---|
| 삼성웰스토리 | `8~10:30OR12~13:30/배송전연락` | `08:00~10:30, 12:00~13:30` |
| 신의유통 | `12시전` | `~12:00` |
| 원앤원 | `점심11~12시30분` | `08:00~11:00, 12:30~18:00` (운영시간 가정) |
| 지키미에프에스 | `오전` | `~12:00` |

**배제 구간 세분화 (10건)** — 외곽 경계는 같지만 컬럼이 점심시간을 담지 못한다.
위 6건과 달리 마감 자체는 맞으므로 정보 등급으로 분류하되, 시간창은 분리해 적용해야 한다.
예) 채움푸드 `8~11또는13~14:30(점심11:30~13)` ↔ 컬럼 `8:00~14:30`

#### (2) 시간창 결손

- 납품시간 컬럼 보유: **41곳 / 55곳** (14곳 빈값)
- 빈값 14곳 중 **4곳은 납품처명에 시간 조건이 존재**(삼성웰스토리·신의유통·원앤원·지키미에프에스"오전") → AI 파싱으로 회수 가능
- 나머지 10곳은 실제 무제약 → 시간창 없음으로 확정

#### (3) 조기납품 기준의 모호성 ⚠️ **의사결정 필요**

`plan.md` §3.2는 "마감 ≤ 09:00"을 조기납품 규칙 판단 기준으로 정의했으나, 실데이터 적용 결과:

제약의 적용 단위는 **기사**다 — 한 기사에게 조기납품 업체를 2곳 이상 배정하지 않는다(R-08).
기사가 9명이므로 조기납품 업체가 9곳을 넘으면 초과분은 **반드시 기타로 빠진다**.

| 기준 | 해당 업체 수 | 결과 (기사 9명 기준) |
|---|---|---|
| 마감 시각 ≤ 09:00 | **0곳** | 규칙이 한 번도 발동하지 않음 |
| 마감 시각 ≤ 10:00 | **3곳** — 대명푸드 `8~10시` · 주아유통 `~10:00` · 태건푸드 `~10:00` | 전량 수용 가능 |
| 시작 시각 ≤ 09:00 | **18곳** | 최소 **9곳 강제 미배차** |

> **판정 구현 시 주의** — 납품 시작 시각 기본값이 08:00이므로(R-16), 마감만 있는 시간창(`~13:30`)은
> `{시작 08:00, 종료 13:30}`으로 표현된다. "시작 ≤ 09:00"을 그대로 적용하면 마감만 있는 배송지가
> 전부 걸려 42곳이 잡히므로, **원문에 시작 시각이 명시된 경우로 한정**해야 한다
> (구현: `hasExplicitStart && w.start <= 09:00`).

→ 현행 정의(`마감 ≤ 09:00`)로는 규칙이 무의미하고, `시작 ≤ 09:00`으로 바꾸면 9곳이 강제로
기타가 된다. **§14 OI-2에서 기준값을 확정해야 한다.**

### 6.1 배차 우선순위 (기타로 밀어낼 때의 판단 순서)

제약이 충돌할 때 시스템이 적용하는 순서를 명시한다.

1. **시간창이 좁은 업체 우선** (마감이 이른 순)
2. **대량 물량 우선** (회전 적재 하한 충족에 유리)
3. **기사 도착지 인접 권역 우선** (귀가 거리)
4. **원거리 단독 업체는 후순위**

이 순서가 적용되기 전에 두 규칙이 후보를 좁힌다.

- **R-18** — 천안 이남은 배차 대상 풀에 아예 들어오지 않는다(용차).
- **R-17** — 대형차(5톤 이상)는 같은 장소에 짝이 없는 소량 업체를 후보로 삼지 않는다.

## 9. 시스템 구성 — 3계층 책임 분리

| 계층 | 담당 | 책임 | 하지 않는 것 |
|---|---|---|---|
| ① 생성형 AI | 비정형 해석 | 납품처 파싱, 시간창 구조화, 조건 태깅, 주소 정제 제안, 결과 요약 | 배차 결정, 좌표 확정 |
| ② 자체 로직 | **차량 간 배분** | 적재 조합, 회전 배정, 권역 묶음, 조기납품 제한, 기타 분류, 규칙 검증 | 방문 순서, 실도로 거리 |
| ③ TMAP | 좌표·순서·경로 | 지오코딩, 차량 1대 내 순서 최적화, 실도로 거리·시간, 지도 | 차량 간 배분 |

### 9.1 파이프라인 (E2E)

```
[1] 업로드·파싱·검증     [자체]        ← FR-01~08
[2] 조건 구조화          [AI] → [자체 검증]  ← FR-10~19
[3] 좌표 변환            [TMAP 지오코딩]     ← FR-20~23
[4] 차량 간 배분         [자체]              ← FR-40~44
[5] 방문 순서 최적화     [TMAP 최적화]       ← FR-24~25   회전당 1회
[6] 시간 검증            [자체 + arriveTime] ← FR-26      위반 시 [4]로 복귀 (1회)
[7] 경로 확정            [TMAP 다중경유지]   ← FR-27
[8] 결과 출력            [TMAP 지도 + AI 요약 + 엑셀]  ← FR-28~29, FR-50
                         ↓
                    세션 데이터 소멸
```

## 10. 산출물 명세 — 결과 엑셀 (공식 문서)

화면은 검토용이고, **보관·공유·수정의 기준 문서는 이 엑셀**이다.

### 시트 1: 배차표
| 컬럼 | 설명 |
|---|---|
| 기사명 / 톤수 / 회전 | 차량 마스터 |
| 방문순서 | TMAP 최적화 결과 순번 |
| 업체명 / 권역 / 주소 | 납품처 파싱 결과 |
| 박스수량 | 재고단위수량 합계 |
| 납품시간(원문) / 납품시간(해석) | AI 구조화 결과 — 원문 병기 |
| TMAP 도착예정시각 | `arriveTime` |
| 시간창 충족 | OK / 경고 |
| 특이사항 태그 | 비대면·안전화·도크 등 |
| 연락처 | 1개 |
| 회전 소계 | 박스 합계, 적재율(%), 업체 수, 주행거리, **귀가거리** |

### 시트 2: 기타_미배차
`권역 / 업체명 / 주소 / 박스수량 / 납품시간 / **사유코드** / 비고` — 용차 판단용. 권역별 소계 표시.

### 시트 3: 주소확인필요
`원문 주소 / 지오코딩 결과 / 실패 유형 / AI 정제 제안 / 비고` — 담당자가 원본 파일을 고칠 때 사용.

### 시트 4: 요약
`출고일자 / 실행시각 / 총 오더 행·제외 행 / 총 납품처·총 박스 / 배차 박스·기타 박스 / 사용 회전 수 / 차량별 적재율 / 제약 위반 건수 / API 호출 건수(API별) / AI 브리핑`

### 시트 5: 좌표 (선택 · 기본 비활성)
`업체명 / 주소 / 위도 / 경도 / 변환 방식` — 다음 실행 시 참고 재업로드용. **약관 확인 후 활성화** (§14 OI-5).

## 11. 화면 요구사항

### ① 배차 보드
- TMAP 지도: 평택센터 구분 마커 / 기사별 색상 마커 / 회전별 실도로 경로선 / 마커 클릭 시 업체명·박스·납품시간 팝업
- 기사별 배차 티켓: 회전별 방문 순서, 박스, 도착예정시각, 적재율 게이지, 특이사항 태그, **귀가 거리**
- 기타(미배차) 권역별 패널 + 주소확인필요 목록
- 상단: 총 물량 / 배차 / 기타 / 사용 회전 / 제약 위반 건수
- **결과 엑셀 다운로드** 버튼, AI 요약 브리핑

### ② 데이터 업로드
- 파일 2개 드래그 업로드 존 (각각 업로드 상태 표시)
- 파싱 요약 카드 (FR-07 지표)
- 구조화 미리보기: **원문 | AI 해석 | 검증 결과** 3열 테이블
- 담당자 확인 목록: 시간창 불일치 6건, 시간창 결손, 박스 수 불일치, 주소 이상, 조기납품 후보
- 차량 마스터는 **읽기 전용 표시** — 수정은 파일 고쳐 재업로드

### ③ 결과 다운로드
- 엑셀 다운로드 버튼 + 시트 구성 안내
- "다운로드 전 페이지를 벗어나면 결과가 사라집니다" 경고
- 좌표 시트 포함 여부 토글 (기본 OFF)

### ④ 설정
- 센터 좌표·출발시각 (기본값 내장, **세션 한정 변경**)
- TMAP 키 상태 (환경변수 설정 여부만 표시, 키 값 노출 금지)
- API 일일 호출 카운터
- Demo Mode 토글
- 설정도 저장하지 않으며 매 실행 기본값에서 시작
